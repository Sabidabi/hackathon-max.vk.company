# Обновление мини-приложения MAX на сервере

Репозиторий: `Sabidabi/hackathon-max.vk.company`. Проверочный бот: [«Синица» в MAX](https://max.ru/t540_hakaton_max_bot). Адрес веб-приложения в настройках бота: `https://max.nii-mvus.ru`.

## На сервере с Docker Compose

В каталоге проекта, где находится рабочий `.env`:

```bash
git pull --ff-only origin main
docker compose config --quiet
docker compose up -d --build frontend backend worker
docker compose ps
docker compose exec backend python -m app.max_api.check_webhook
```

После `git pull` пересоберите контейнеры: уже запущенный frontend сам не обновится. Рабочий `.env` оставьте на сервере.

Проверка подписки читает `GET /subscriptions` у MAX и не выводит токен. В ответе должны быть `subscription_found: true`, `bot_started: true` и `message_created: true`. Если подписка пропала или события не включены, проверьте `MAX_WEBHOOK_URL`: это должен быть публичный `https://max.nii-mvus.ru/webhooks/max` с действующим сертификатом. Затем на сервере выполните `docker compose exec backend python -m app.max_api.setup_webhook` и повторите проверку. Эта команда меняет подписку бота в MAX, поэтому её выполняют только для нужного бота и серверного `.env`.

В настройках этого бота на платформе MAX должен быть указан публичный **HTTPS URL веб-приложения** и включена кнопка запуска мини-приложения. В серверном `.env` проверьте без публикации значений: `APP_ENV=production`, `DEV_AUTH_ENABLED=false`, `MAX_BOT_USERNAME=t540_hakaton_max_bot`, `MAX_BOT_TOKEN` от того же бота и `PUBLIC_APP_URL` с тем же HTTPS-адресом. Если используется webhook, проверьте также его HTTPS-адрес и secret.

## Проверка после обновления

1. На публичном адресе `/api/v1/health/ready` должен быть успешный ответ, а `/api/v1/auth/bootstrap` должен показывать `max_auth_configured: true` и `development_auth: false`.
2. Откройте чат с ботом с нового тестового аккаунта или отправьте `/start`. Бот должен ответить приветствием и кнопкой «Открыть Синицу». Если ответа нет, сначала проверьте подписку командой выше, затем `docker compose logs --tail=100 backend worker` без публикации секретов.
3. Закройте старое окно мини-приложения в MAX и откройте его через кнопку бота. В новом интерфейсе больше нет фразы «Откройте кабинет в MAX».
4. Если вход всё ещё не проходит, отправьте боту `/start` и нажмите **новую** кнопку в ответе: теперь бот посылает тип `open_app`. Старые сообщения с прежней кнопкой не изменятся.
5. Проверьте создание точки, публикацию меню и гостевую ссылку. Не передавайте в переписке `WebAppData`, bot token или полный URL с fragment после `#`.

Если после обновления появляется «Не удалось подтвердить вход», проверьте подпись и срок действия данных запуска. Если внутри MAX появляется «Откройте в MAX», проверьте HTTPS-адрес и способ открытия мини-приложения через бота. После развёртывания запишите SHA запущенного коммита и результат проверки на телефоне.

## Чек-лист ручной проверки в MAX

Проверяйте на тестовом аккаунте в мобильном и веб-клиенте MAX при `APP_ENV=production` и `DEV_AUTH_ENABLED=false`. Рассылку отправляйте только на свой аккаунт с включённым согласием. Рядом с каждым результатом запишите дату и версию клиента.

Перед проверкой: сервер собран из проверенного коммита, на сервере выполнен `python -m app.demo_seed` (или своё тестовое заведение), `npm run test:live` зелёный на этом коммите.
