# ИИ и MCP

## ИИ-функции

Все функции идут через один шлюз (`backend/app/ai/service.py`) и порт провайдера (`backend/app/ai/provider.py`).

| Функция | Эндпоинт | Что пишет |
| --- | --- | --- |
| «Синица, что взять?» (гость) | `POST /public/restaurants/{public_id}/ask` | Ничего. До 3 доступных позиций опубликованного меню, цены из снимка сервера |
| Описание позиции (админ) | `POST /menus/{id}/ai/description` | Ничего. Текст попадает в форму и в черновик обычным автосохранением |
| «Синица проверила меню» | `POST /menus/{id}/check` | Ничего. Замечания считает код, ИИ формулирует итог и подсказки |
| Создание позиций текстом | план и применение (`menu_ai`) | Только черновик, после подтверждения |
| Структурирование импорта | worker после OCR | Только результат разбора → экран проверки → «Применить в черновик» |
| Недельная сводка | `GET analytics/ai-summary` | Ничего. Числа проверяются кодом |

## Провайдер

ИИ работает через OpenAI-совместимый шлюз.

```dotenv
AI_PROVIDER=auto            # auto | openai | mock | off
AI_BASE_URL=https://routerai.ru/api/v1
AI_API_KEY=
AI_MODEL=qwen/qwen3.8-omni-flash
```

- `auto` и `openai` — шлюз при заданном `AI_API_KEY`. Без ключа ИИ честно недоступен: гостю показывается подборка без ИИ, импорт использует эвристический разбор.
- `mock` — офлайн-адаптер для демо и CI. Ответы помечаются `provider: "mock"`, интерфейс показывает «Демо-ИИ».
- `off` — ИИ всегда недоступен.
- `GET /ai/status` и признак `assistant` в публичном меню сообщают состояние без вызова модели.

Ключ хранится только в `.env`. Пример в репозитории содержит пустое значение.

## Лимиты и учёт

Учёт ведётся в таблице `ai_usage`: принятые запросы (`calls`) и реальные вызовы модели (`provider_calls`) по заведению и дню.

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `AI_GUEST_DAILY_LIMIT` | 20 | запросов гостя в сутки (пользователь MAX или хеш IP и User-Agent) |
| `AI_ADMIN_DAILY_LIMIT` | 100 | запросов администратора в сутки |
| `AI_VENUE_DAILY_LIMIT` | 500 | все функции заведения в сутки |
| `AI_GUEST_IP_DAILY_LIMIT` | 100 | анонимные гости с одного адреса |
| `AI_GUEST_VENUE_SHARE_PERCENT` | 70 | доля бюджета заведения для гостей, остаток — резерв админа |
| `AI_REQUEST_TIMEOUT_SECONDS` | 20 | тайм-аут вызова модели |
| `AI_CACHE_TTL_SECONDS` | 600 | кэш одинаковых запросов в процессе |
| `AI_IMPORT_STRUCTURING` | true | структурирование импорта |
| `AI_PROPOSAL_TTL_SECONDS` | 600 | срок плана изменений меню до подтверждения |

Превышение даёт 429 с `detail.code` `ai_limit_user` или `ai_limit_venue`; гостю в `detail.items` приходит подборка без ИИ. В логах только имя задачи, провайдер и время, без промптов и текста гостя.

## Защита от prompt-injection

- Инструкции задаёт только код. Вопрос гостя, текст OCR и поля позиции передаются как JSON внутри `<data>…</data>` с экранированием `<` и `>`.
- Ответ модели — вызов функции с аргументами по строгой схеме Pydantic (`extra=forbid`). Невалидный ответ считается «ИИ недоступен».
- После схемы работают проверки кода:
  - ID позиций только из списка доступных позиций точки (стоп-лист и часы показа учтены);
  - цена из импорта сохраняется, только если число буквально есть в тексте;
  - описание отклоняется, если содержит числа и факты (ккал, аллергены, «без глютена», цены), которых нет в карточке;
  - числа недельной сводки сверяются с данными.
- ИИ не публикует: результат попадает в черновик или на экран проверки.

## MCP-сервер меню

MCP даёт внешнему ИИ-агенту стандартные ограниченные инструменты работы с черновиком меню. У агента нет SQL, shell и произвольных URL.

```text
Кнопка «Создать с ИИ» → backend → шлюз ИИ → план изменений ─┐
                                                             ├─ подтверждение → сервис команд меню → черновик
Внешний ИИ-агент → MCP-сервер ───────────────────────────────┘
```

Изменения применяются только через сервис команд меню (`backend/app/menu_commands/`): проверка ролей, организации, ревизии, цен и модификаторов. REST и MCP не имеют собственной бизнес-логики.

### Инструменты

- `get_menu_context` — краткий контекст черновика: точка, разделы, карточки, текущая `revision`, валюта, лимиты. Без токенов, персональных данных и платежей.
- `propose_menu_change` — принимает план и `expected_revision`, ничего не записывает. Возвращает diff, предупреждения и одноразовый `confirmation_token`. Отсутствующие цену или объём не выдумывает.
- `apply_menu_change` — принимает `confirmation_token` и `expected_revision`, пишет только в черновик. Токен одноразовый, с TTL, связан с организацией, пользователем, хешем плана и ревизией. Повтор, подмена плана или изменение черновика дают ошибку.
- `get_change_result` — выполненные операции, новые UUID и новая ревизия; помогает не создать позицию повторно.

Цены в плане — в копейках (190 ₽ = `19000`).

### Чего MCP не делает

Не публикует меню и оформление, не принимает платежи, не меняет роли, не читает чужие заведения, не загружает произвольные URL, не выполняет SQL, shell и код, не применяет план без подтверждения.

### Аутентификация и изоляция

`restaurant_id` из аргументов модели доступом не считается. Токен привязан к своей организации, точкам и областям:

- `menu:read` — контекст и результат;
- `menu:propose` — проверка плана;
- `menu:write` — применение подтверждённого плана.

Каждый вызов журналируется: субъект, организация, инструмент, ID запроса, хеш аргументов, результат, без секретов и промптов.

### Настройка

```dotenv
MCP_ENABLED=false
MCP_RESOURCE_URL=http://127.0.0.1:8010/mcp
MCP_ISSUER_URL=http://127.0.0.1:8010
MCP_CONFIRMATION_TTL_SECONDS=600
```

1. Примените миграции и узнайте UUID точки и пользователя.
2. Выпустите токен. Он показывается один раз, в БД хранится только SHA-256:

```bash
cd backend
python -m app.mcp_server.issue_token --restaurant-id RESTAURANT_UUID --user-id USER_UUID --client-id ai-agent
```

3. Задайте `MCP_ENABLED=true` и запустите отдельный процесс:

```bash
uvicorn app.mcp_server.server:app --host 127.0.0.1 --port 8010
# или
docker compose --profile mcp up --build
```

4. Клиент `ai-agent` подключается к `http://127.0.0.1:8010/mcp` с заголовком `Authorization: Bearer <token>`. Порядок вызовов: `get_menu_context` → `propose_menu_change` → показ diff человеку → `apply_menu_change`.

В продакшне endpoint должен работать по HTTPS, токены — короткоживущими из хранилища секретов, общий статический ключ для всех клиентов недопустим. Транспорт `stdio` намеренно не включён.

### Проверка

Тесты покрывают список инструментов, отсутствие инструмента публикации, строгую JSON-схему, области доступа, привязку токена к пользователю, хеширование секретов. Проверки изоляции заведений, срока действия и повторного применения требуют тестовой PostgreSQL (`RUN_DB_INTEGRATION=1`).

Документация протокола: [Официальный MCP Python SDK](https://py.sdk.modelcontextprotocol.io/).
