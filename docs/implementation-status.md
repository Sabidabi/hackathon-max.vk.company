# Статус реализации

Обновлено: 26.09.2026. Репозиторий подготовлен как проверяемый этап редактора меню. Реальные платежи и production-вызовы внешних сервисов не выполнялись.

## Несколько точек и команда (FR-03, FR-10a, FR-10b, AC-03)

- Владелец создаёт несколько точек; в кабинете есть переключатель и ссылка `/manage/{public_id}`. Ссылка не выдаёт права: доступ проверяется сервером.
- «Библиотека» показывает опубликованные и архивные версии владельца. Копирование восстанавливает выбранную версию в черновик точки; фотографии копируются в её хранилище. Публикация остаётся отдельным действием.
- Наличие позиции можно задать сразу в выбранных точках. Сервер сопоставляет уникальные пары «раздел + название», блокирует черновики в стабильном порядке, проверяет ревизии и применяет всё одной транзакцией. При конфликте ничего не меняется.
- Владелец приглашает сотрудника по числовому MAX ID на роль редактора или управляющего, может изменить роль и отозвать доступ. Токен приглашения хранится только как SHA-256 хеш, действует сутки и используется один раз. Команда бота `/id` возвращает свой ID.
- На локальной PostgreSQL применена миграция `0008`; интеграционный сценарий проверил создание двух точек, копирование, массовое наличие, чужой доступ, одноразовое приглашение и отзыв. Общий прогон: 92 passed, 1 deselected (OCR/Tesseract). Ruff, frontend build и browser smoke проходят. Backend отдельно запущен с тестовой БД: `/health/live` и `/health/ready` ответили успешно, новые маршруты есть в OpenAPI. Browser fixture проверяет создание второй точки, библиотеку, приглашение и мобильную ширину 390 px. Реальный MAX и production Docker остаются непроверенными.
- [Спецификация и задачи](specs/multi-point-menu.md). Подход Spec Kit применён как документация без установки CLI. Caveman установлен в личные навыки Codex. Установка исполняемого пакета Graphify была отклонена автоматической проверкой риска внешней зависимости; карта связей записана вручную в спецификации.

## Исправление запуска в MAX (FR-01, FR-02, AC-04)

- Вход больше не зависит от единственного чтения `window.WebApp` при загрузке модуля: фронтенд ждёт позднее появление моста и читает подписанный `WebAppData` из fragment, если мост не передал `initData`.
- `start_param` читается из передаваемых на сервер данных; права доступа по-прежнему определяет сервер. Проверка подписи и срока действия `initData` на сервере не ослаблена. Публичное меню по `/r/...` открывается без ожидания моста; кабинет без данных входа показывает понятное состояние.
- Browser smoke с фикстурой проверяет запуск через fragment, поздний мост, однократную отправку данных входа и немедленное открытие публичного меню. Это не подтверждает поведение реального клиента MAX и production-конфигурации бота.
- Проверки 25.09.2026: frontend production build — успешно; browser smoke — успешно; Ruff — успешно; backend pytest — 84 passed, 2 skipped (нет отдельной PostgreSQL), 1 deselected (OCR/Tesseract); `docker compose config --quiet` — успешно с предупреждением о недоступном локальном Docker config. PostgreSQL на 55432 не запущена; integration-тесты и повтор миграций на этом компьютере в текущем запуске не проводились.
- После развёртывания этого коммита требуется фактический вход из MAX на мобильном и веб-клиенте. Если сервер вернёт 401/503, отдельно проверить соответствие `MAX_BOT_TOKEN` боту, URL mini app и серверные логи без публикации подписанных данных.

## Готово

- Создание точки, ролевая проверка доступа и отдельный черновик меню.
- Редактор категорий и карточек: фото, цена в копейках, описание, стоп-лист, размеры, добавки и обязательные группы выбора.
- Импорт PDF/JPG/PNG с OCR, экраном проверки и ручным применением.
- GigaChat-команда вида «создай капучино…»: строгий план, предпросмотр и применение только в актуальный черновик.
- MCP для чтения контекста, создания плана и подтверждённого изменения черновика. Токен ограничен пользователем, точкой и scopes; публикация через MCP запрещена.
- Оформление меню: четыре обновлённых шаблона «Минимал», «Бистро», «Поп» и «Ночь» с миниатюрами, согласованные светлая/тёмная палитры, фон, цвета и размер шрифта.
- Гостевой каталог в стиле мобильного приложения ресторана: меню сразу после обложки, поиск, фильтр наличия, липкая горизонтальная лента категорий, карточки в 2–3 колонки и нижняя панель позиции на телефоне.
- Загрузка фотографии вынесена в заметный блок карточки товара; каталог и предпросмотр имеют компактное состояние без фото.
- Публикация неизменяемой версии, публичная ссылка и QR-код.
- Избранное и MAX-рассылки только по согласию: outbox, дедупликация, тихие часы, лимиты и повторная проверка подписки. Изменения черновика уведомлений не создают.
- Краткая документация продукта, дизайна, AI-правил, MCP и дальнейшего плана.

## Проход по премиальному гостевому меню (26.09.2026)

- Убраны декоративные псевдофото у позиций без снимка. Если вся категория без фото, она показана как компактный редакционный список; загруженные владельцем фотографии остаются крупными карточками. То же правило действует в предпросмотре.
- Обновлены типографика, обложка, ритм секций и микродвижение. Анимации отключаются при `prefers-reduced-motion`, прокрутка категорий учитывает эту настройку.
- Проверены production-сборка фронтенда и browser smoke с тестовым API; визуально просмотрен мобильный экран 390 px. Реальный MAX и производственный сервер в этом проходе не проверялись.
- Следующий дизайн-проход: фотографии настоящих блюд и обложки от заведения, доработка детальной карточки и проверка светлых тем на реальных меню. Не подменять фотографии блюд вымышленными AI-изображениями.

## Исправление запуска демо (26.09.2026)

- Причина пустой гостевой страницы: пользователю был запущен тестовый сервер с неопубликованным черновиком. Ответ HTML 200 не подтверждал наличие публичного меню. Введена команда `npm run demo` с опубликованным синтетическим снимком; тест редактора по-прежнему начинает без публикации.
- Для гостевого экрана ошибки добавлена кнопка повторного запроса, компактная типографика и видимый клавиатурный фокус (применён frontend-design).
- В browser smoke добавлен отдельный свежий процесс демо: прямое открытие гостевой ссылки, видимость блюда, цена при выборе молока, перезагрузка и восстановление после HTTP 503 на 320/390/1280 px. Применён подход webapp-testing: дождаться отрисовки, проверить действия, ошибки страницы и скриншоты. Используется уже установленный Node Playwright проекта; Python Playwright локально отсутствует.
- Связь с требованиями: гостевое чтение позиций FR-06; локальная демонстрация и синтетические данные относятся к AC-13, но не заменяют его проверку Docker/миграций.
- Фактически прошли frontend build, оба browser smoke и отдельная проверка живого адреса `127.0.0.1:5173/r/test-point`. Производственная публикация, MAX-вход, база и интеграции этим не проверяются.
