# Статус реализации

Обновлено: 25.09.2026. Репозиторий подготовлен как проверяемый этап редактора меню. Реальные платежи и production-вызовы внешних сервисов не выполнялись.

## Исправление запуска в MAX (FR-01, FR-02, AC-04)

- Вход больше не зависит от единственного чтения `window.WebApp` при загрузке модуля: фронтенд ждёт позднее появление моста и читает подписанный `WebAppData` из fragment, если мост не передал `initData`.
- `start_param` читается из передаваемых на сервер данных; права доступа по-прежнему определяет сервер. Проверка подписи и срока действия `initData` на сервере не ослаблена. Публичное меню по `/r/...` открывается без ожидания моста; кабинет без данных входа показывает понятное состояние.
- Browser smoke с фикстурой проверяет запуск через fragment, поздний мост, однократную отправку данных входа и немедленное открытие публичного меню. Это не подтверждает поведение реального клиента MAX и production-конфигурации бота.
- Проверки 25.09.2026: frontend production build — успешно; browser smoke — успешно; Ruff — успешно; backend pytest — 84 passed, 2 skipped (нет отдельной PostgreSQL), 1 deselected (OCR/Tesseract); `docker compose config --quiet` — успешно с предупреждением о недоступном локальном Docker config. PostgreSQL на 55432 не запущена; integration-тесты и повтор миграций на этом компьютере в текущем запуске не проводились.
- После развёртывания этого коммита требуется фактический вход из MAX на мобильном и веб-клиенте. Если сервер вернёт 401/503, отдельно проверить соответствие `MAX_BOT_TOKEN` боту, URL mini app и серверные логи без публикации подписанных данных.

## Готово

- Создание точки, ролевая проверка доступа и отдельный черновик меню.
- Редактор категорий и карточек: фото, цена в копейках, описание, стоп-лист, размеры, добавки и обязательные группы выбора.
- Импорт PDF/JPG/PNG с OCR, экраном проверки и ручным применением.
- GigaChat-команда вида «создай капучино…»: строгий план, предпросмотр и применение только в актуальный черновик.
- MCP для чтения контекста, создания плана и подтверждённого изменения черновика. Токен ограничен пользователем, точкой и scopes; публикация через MCP запрещена.
- Оформление меню: четыре обновлённых шаблона «Минимал», «Бистро», «Поп» и «Ночь» с миниатюрами, согласованные светлая/тёмная палитры, фон, цвета и размер шрифта.
- Гостевой каталог в стиле мобильного приложения ресторана: меню сразу после обложки, поиск, фильтр наличия, липкая горизонтальная лента категорий, карточки в 2–3 колонки и нижняя панель позиции на телефоне.
- Загрузка фотографии вынесена в заметный блок карточки товара; каталог и предпросмотр имеют компактное состояние без фото.
- Публикация неизменяемой версии, публичная ссылка и QR-код.
- Избранное и MAX-рассылки только по согласию: outbox, дедупликация, тихие часы, лимиты и повторная проверка подписки. Изменения черновика уведомлений не создают.
- Краткая документация продукта, дизайна, AI-правил, MCP и дальнейшего плана.

## Проверено

- Backend: Ruff и 86 тестов, включая integration-сценарии на локальной PostgreSQL; миграции `0001`–`0007` применены последовательно. OCR-тест требует установленный Tesseract и запускается отдельно.
- Frontend: TypeScript/Vite production build и browser smoke для заметной загрузки фото, AI-карточки, редактора, обязательных добавок, серверной цены, тёмной темы, публикации, QR, избранного, opt-in рассылки, горизонтальных категорий и ширины 390 px.
- Исправлены найденные UX-регрессии: цвета гостевых карточек и заголовка больше не перезаписываются стилями кабинета; тёмная тема меняет полную палитру; недоступная позиция получает явное состояние; активная категория остаётся видимой в горизонтальной ленте.
- Секреты, `.env`, сборки, зависимости и временные файлы исключены из Git.

Полный Compose-запуск на текущем компьютере заблокирован сбоем Docker Desktop 4.47.0 при инициализации локального `dockerInference` socket. `docker compose config --quiet` проходит; сбой возникает в Docker до запуска сервисов проекта. Для проверки приложение поднято напрямую: Vite, FastAPI, worker и локальная PostgreSQL на порту 55432.

## Перед production

1. Создать отдельного тестового MAX-бота, подключить HTTPS mini app/webhook и пройти основной путь внутри MAX.
2. Перед релизом повторить миграции и integration-тесты в CI на чистой PostgreSQL: изоляция организаций, повтор webhook/outbox и MCP HTTP auth.
3. Проверить тестовый GigaChat credential: один AI-план и применение в черновик без production-данных.
4. Провести пилот на 3–5 реальных меню и поправить UX по наблюдениям.
