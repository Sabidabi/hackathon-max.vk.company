# Декомпозиция следующего этапа

Обновлено: 21.09.2026. Порядок выбран по зависимостям и риску. Новые возможности не считаются готовыми, пока не выполнены их критерии приёмки и проверки из последней колонки.

**Фактический прогресс:** локально реализованы MAX-01, первая операция MENU-01 (`create_item`), AI-01/02/03, MCP-01, DESIGN-01–04 и NOTIFY-01/02. Полная матрица команд MENU-01, PostgreSQL integration, реальные MAX/GigaChat credentials, IMAGE-01 и MOTION-01 остаются незакрытыми. Проверки перечислены в `implementation-status.md`.

## Принципы этапа

- MAX — основной канал владельца. Внутри мини-приложения вход выполняется автоматически по подписанному `window.WebApp.initData`; сервер проверяет подпись и срок действия. Обычный браузер не получает обходной производственный вход.
- Нейросеть не пишет строки меню напрямую. Она формирует типизированный план изменений, сервер валидирует его, владелец видит результат и явно применяет в актуальный черновик.
- REST-интерфейс, интерфейс редактора и MCP используют один сервис команд меню. Это предотвращает три несовместимые реализации одной операции.
- Все деньги остаются целыми копейками. Организация, роль, ревизия черновика, размеры и модификаторы проверяются сервером.
- Оформление является версионируемой конфигурацией. Сгенерированное изображение сначала попадает в черновик и не публикуется автоматически.

## P0 — основание, без которого нельзя безопасно продолжать

### MAX-02. Тестовый бот и mini app внутри MAX

**Задача:** создать отдельного тестового бота, подключить HTTPS-адрес приложения и webhook, затем выполнять приёмку основного пользовательского пути непосредственно внутри MAX.

**Подзадачи:** настроить `MAX_BOT_TOKEN`, имя бота, webhook secret/URL и public app URL через `.env`; зарегистрировать webhook штатной командой; проверить `initData`, deep links и повторный вход; пройти создание точки, публикацию, QR, AI-план и одно служебное уведомление; записать результат и версию клиента в `implementation-status.md`.

**Готово, когда:** тестовый пользователь открывает mini app из бота без ручного логина, сервер валидирует `initData`, а базовый путь проходит в MAX без браузерных заглушек. Секреты не попадают в Git или логи.

### MAX-01. Автоматический запуск кабинета из MAX

**Задача:** убрать ручную карточку «Войти в кабинет». При старте клиент запрашивает текущую сессию; при её отсутствии внутри MAX автоматически отправляет `initData` на `/auth/max`. В development допускается отдельный автоматический dev-вход, который отключён в production.

**Подзадачи:**

- подключить официальный MAX Bridge до запуска React и вызвать `ready/expand` после чтения данных;
- добавить публичный bootstrap-ответ сервера: настроен ли бот, разрешён ли dev-вход и какая безопасная MAX deep link доступна;
- различить состояния `starting`, `authenticating`, `ready`, `MAX required`, `server unavailable`;
- вместо большой заглушки показывать компактный полноэкранный индикатор запуска; при production-запуске вне MAX — одну кнопку перехода к боту;
- сохранить серверную валидацию подписи, возраста и повторяющихся параметров;
- проверить cookie на HTTPS, выход и повторный вход.

**Готово, когда:** запуск из MAX не требует нажатия входа; development открывается без ручной кнопки; production вне MAX не создаёт сессию; неверный `initData` отклоняется.

**Тесты:** unit для bootstrap/state machine и MAX bridge; backend auth tests; browser fixture для MAX/dev/production состояний.

### MENU-01. Единый сервис команд меню

**Задача:** вынести операции создания и изменения категорий/карточек из HTTP-роутов в прикладной слой, который смогут вызывать ручной редактор, GigaChat и MCP.

**Команды первой версии:**

- `create_section`;
- `create_item`;
- `update_item`;
- `set_variants`;
- `set_modifier_groups`;
- `set_availability`.

**Инварианты:** команда работает только с доступной пользователю точкой; содержит `expected_revision`; использует стабильные UUID; не публикует меню; проверяет RUB, копейки, размеры, min/max/default и доступность; конфликт возвращает 409.

**Готово, когда:** существующий ручной редактор и новый AI endpoint применяют изменения через одинаковую функцию; прямого обхода валидации нет.

**Тесты:** unit каждого типа команды, неизвестных ID, чужой точки, устаревшей ревизии и повторной отправки.

### TEST-01. Базовый контур качества

**Задача:** добавить отдельные команды `test:unit`, `test:browser`, backend unit/integration и единый локальный check-script.

**Подзадачи:**

- Vitest + React Testing Library для чистой UI-логики и компонентов;
- pytest для доменных сервисов, GigaChat-клиента через mock transport и MAX bootstrap;
- Playwright для главных пользовательских цепочек;
- тестовая PostgreSQL для миграций, изоляции организаций и конкурентных ревизий;
- фиксировать пропуски инфраструктурных тестов в `implementation-status.md`.

**Готово, когда:** одна команда проверяет типы, линтер, backend unit, frontend unit и browser smoke; integration запускается отдельно только на тестовой БД.

## P1 — создание карточек меню через естественный язык

### AI-01. Типизированный план изменений

**Задача:** описать `MenuChangePlan`, который нейросеть обязана вернуть перед применением.

Пример запроса владельца: «Добавь капучино 250 и 350 мл, цены 190 и 240 ₽. Выбор молока обязательный: обычное бесплатно, овсяное +60 ₽. Сиропы необязательные, максимум два».

Ожидаемый план содержит:

- раздел назначения, новую карточку и краткое описание;
- размеры с абсолютными ценами в копейках и размер по умолчанию;
- обязательную группу молока `min=1/max=1`;
- необязательную группу сиропов `min=0/max=2`;
- предупреждения о данных, которые пользователь не указал;
- текстовое резюме и список фактических операций.

**Правила:** отсутствующие цены, состав и аллергены не угадывать; неоднозначные суммы помечать; неизвестный раздел можно предложить создать; ни один план не публикуется автоматически.

**Готово, когда:** один и тот же JSON проходит Pydantic/TypeScript schema и превращается в доменные команды без произвольного кода.

### AI-02. Провайдер GigaChat

**Задача:** серверный клиент GigaChat получает OAuth-токен, вызывает `/v1/chat/completions` и запрашивает структурированный план или аргументы функции `propose_menu_change`.

**Конфигурация:** `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_BASE_URL`, OAuth URL и тайм-аут. Секрет хранится только на сервере; браузер его не получает. Токен кэшируется не дольше срока действия.

**Надёжность:** лимит длины промпта; тайм-аут; request ID; понятные 503/422; отсутствие исходного `.env` в логах; запрет на автоматический retry мутаций; валидация любого ответа модели.

**Готово, когда:** запрос из примера создаёт валидный план; испорченный JSON и невозможные лимиты отклоняются; отсутствие ключа показывает «GigaChat не настроен», не фиктивный успех.

### AI-03. AI-композер в редакторе

**Задача:** компактная кнопка «Создать с ИИ» открывает диалог с одним полем запроса и примерами. После ответа показывается diff: раздел, карточка, размеры, добавки и итоговые цены.

**Действия:** «Применить в черновик», «Изменить запрос», «Отмена». Применение требует текущую ревизию; конфликт не стирает ручные правки. После применения открывается обычная карточка товара для проверки.

**Готово, когда:** владелец создаёт капучино из примера без ручного заполнения каждой строки, проверяет результат и видит его в черновике; публикация остаётся отдельным действием.

**Тесты:** компонентные состояния loading/error/preview/conflict; browser flow prompt → preview → apply → edit → publish.

### MCP-01. MCP-адаптер редактора меню

**Задача:** поднять отдельный MCP server на официальном Python SDK `mcp` с инструментами поверх `MENU-01`.

**Инструменты первой версии:**

- `get_menu_context` — краткий черновик, ревизия и ограничения;
- `propose_menu_change` — валидация структурированного плана без записи;
- `apply_menu_change` — запись только с `expected_revision` и явным `confirmation_token` из предложения;
- `get_change_result` — результат и новая ревизия.

**Безопасность:** MCP не принимает произвольный `restaurant_id` без сопоставленной сервером организации; токен инструмента хранится в secret storage; scope минимум `menu:read/menu:write`; журналируется actor/provider/request ID; результаты предложения имеют TTL и одноразовый confirmation token; публикация не является MCP-инструментом первой версии.

**Готово, когда:** GigaChat-агент или другой MCP-клиент может прочитать контекст, предложить карточку и применить подтверждённый план, но не может менять чужую точку или обходить ревизию.

**Тесты:** contract tests MCP tools, token scope, tenant isolation, expired confirmation, replay и revision conflict.

## P1 — оформление и светлая/тёмная тема

### DESIGN-01. Токены оформления

**Задача:** расширить `SiteConfig` без поломки старых черновиков.

Новые поля: `theme_mode` (`light/dark`), `icon_color`, `text_color`, `surface_color`, `background_image_url`, `background_overlay`, `font_scale` в ограниченном диапазоне. Цвета валидируются как hex, URL изображения — только собственное media точки.

**Готово, когда:** старые конфигурации мигрируют с безопасными значениями по умолчанию; черновик и опубликованная версия воспроизводят одинаковый дизайн.

### DESIGN-02. Готовые шаблоны

**Задача:** превратить Modern/Classic/Cafe в полные пресеты токенов и добавить минимум один тёмный пресет. Выбор шаблона — отдельные визуальные кнопки с мини-превью, без длинного текста.

**Готово, когда:** шаблон меняет согласованный набор токенов, после чего любой цвет можно донастроить отдельно; переключение не меняет содержимое меню.

### DESIGN-03. Панель настройки и переключатель темы

**Задача:** отдельные компактные кнопки для светлой/тёмной темы, фона, основного цвета и цвета иконок. Цветовые поля открываются по нажатию; рядом показываются готовые палитры и «Сбросить».

**Готово, когда:** изменения сразу видны в мобильном предпросмотре; состояние сохраняется и публикуется; текст, кнопки и focus ring сохраняют читаемость.

**Тесты:** schema migration, сериализация, выбор пресета, переключение темы, CSS variables, контраст ключевых комбинаций и скриншоты 390/1280 px.

### DESIGN-04. Фоновое изображение

**Задача:** загрузка собственного JPG/PNG в отдельный вид media `background`, управление затемнением/осветлением, удаление и fallback на цвет.

**Готово, когда:** изображение принадлежит точке, оптимизируется сервером, не делает текст нечитаемым и одинаково отображается в preview/публичном меню.

## P2 — генерация фоновых изображений

### IMAGE-01. Безопасный генератор фона

**Задача:** отдельный endpoint принимает короткое описание и вызывает разрешённый image provider. Для GigaChat используется встроенная `text2image`, если тариф и API это поддерживают.

**Поток:** запрос → статус задачи → превью → «Использовать как фон» → сохранение в media точки. Генерация не заменяет фон и не публикует оформление автоматически.

**Ограничения:** квота на организацию, тайм-аут, размер и формат, модерация провайдера, удаление временного результата, учёт стоимости запроса без раскрытия токена.

**Готово, когда:** успешный результат можно проверить и применить; ошибка/тайм-аут не портят текущий дизайн; повторное применение идемпотентно.

## P2 — уведомления через MAX без спама

### NOTIFY-01. Служебное уведомление о публикации

**Задача:** после успешной публикации новой версии отправить владельцу точки одно короткое сообщение через MAX Bot API. Черновые сохранения, изменение порядка и стоп-листа до публикации сообщений не создают.

**Безопасность:** событие имеет уникальный ключ `menu_version_id + recipient_id`; повторная обработка не отправляет дубль; сбой MAX не откатывает публикацию; в тексте нет состава черновика и персональных данных.

### NOTIFY-02. Рассылка подписчикам точки

**Задача:** владелец или управляющий создаёт короткую кампанию для пользователей, которые добавили точку в избранное и отдельно разрешили уведомления.

**Поток:** текст и ссылка → предпросмотр → оценка числа получателей → явная отправка → фоновая очередь → отчёт доставлено/ошибка. Обязательны кнопка отписки, лимит длины и журнал автора.

**Антиспам:** не чаще одной маркетинговой рассылки от точки за 72 часа; не более двух в неделю одному пользователю суммарно; тихие часы по Москве 21:00–09:00; дедупликация; исключение отписавшихся и заблокировавших бота. Системные статусы заказа считаются отдельно.

**Готово, когда:** повторный запуск кампании не создаёт дублей; пользователь может отключить рассылку; чужая точка не видит подписчиков и кампании; лимиты проверяются сервером до постановки в очередь.

## P3 — премиальные продуктовые анимации

### MOTION-01. Система движения

**Задача:** после стабилизации экранов определить токены duration/easing и добавить короткие переходы для диалогов, вкладок, сохранения, публикации и смены темы.

**Правила:** анимация объясняет изменение состояния; `prefers-reduced-motion` отключает необязательное движение; никаких задержек в редактировании и оплате; размер JS не растёт без измеримой причины.

**Готово, когда:** motion review пройден на телефоне и desktop, reduced motion работает, browser tests не становятся нестабильными.
