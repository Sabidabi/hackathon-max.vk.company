# Синица — меню кофейни в MAX

«Синица» помогает небольшой кофейне запустить меню в MAX без отдельного приложения. Владелец создаёт точку, собирает меню и печатает QR. Гость открывает меню, выбирает размер напитка и добавки, а готовый список показывает кассиру. Изменения меню и оформления сначала попадают в черновик: владелец видит их до публикации.

Для проверки в MAX: [бот «Синица»](https://max.ru/t540_hakaton_max_bot). Веб-адрес проекта: [max.nii-mvus.ru](https://max.nii-mvus.ru). Демо с тестовыми данными можно запустить локально по инструкции ниже.

## Что уже работает

- Меню по ссылке и QR, категории, поиск, фотографии, размеры и обязательные группы добавок. Итоговая цена рассчитывается на сервере в копейках.
- Кабинет владельца: несколько точек, библиотека меню, копия меню для другой точки, наличие и цена по точкам, редактор оформления, публикация и QR для печати.
- «Помощь Синицы»: разбор меню из фото или PDF, создание карточек по тексту, проверка меню и предложение оформления. Владелец просматривает результат и сам применяет его к черновику.
- Вход через MAX, доступы администраторов, бот и уведомления для гостей, которые дали согласие.

Сейчас гость **показывает выбор на кассе**. Предзаказ к определённому времени, оплата через ЮKassa, возвраты, экран бариста и отчёт по продажам запланированы, но в этой версии не работают. [Состояние проекта и следующие шаги](docs/implementation-status.md).

## Как выглядит основной путь

### Владелец

1. Открывает бот в MAX и переходит в кабинет. При первом входе создаёт заведение и точку: название, адрес и часовой пояс. У точки сразу появляется собственная ссылка.
2. Выбирает, как собрать меню: добавить позиции вручную, загрузить фото/PDF или попросить «Помощь Синицы» создать карточки по описанию. Например: «Капучино 300 мл — 190 ₽, 400 мл — 230 ₽; молоко выбрать обязательно». Ответ ИИ — предложение, которое можно проверить и отклонить.
3. Проверяет цены, размеры, добавки и фотографии. Если несколько точек продают одно и то же, назначает им общее меню. Если ассортимент разный, делает копию меню. Наличие и цену позиции можно менять отдельно для точки.
4. Настраивает цвета, типографику и вид карточек в разделе «Оформление». Предпросмотр показывает будущий вид гостевого меню. Затем публикует меню и оформление — это два отдельных действия.
5. Скачивает QR и настольную карточку A6 в разделе «Ещё», ставит их у кассы. После изменений снова публикует меню; стоп-лист точки действует сразу.

### Гость

1. Сканирует QR или открывает ссылку точки в MAX. Видит опубликованное меню и доступные сейчас позиции.
2. Открывает карточку напитка, выбирает размер и обязательные добавки. Перед добавлением видит итоговую цену с учётом выбора.
3. Собирает «Мой выбор» и показывает его кассиру. Оплата происходит на кассе; кнопка в приложении не списывает деньги.
4. Может сохранить точку в избранном и отдельно согласиться на уведомления от неё.

В тестовом заведении удобно пройти путь на латте: 350 мл за 230 ₽ и овсяное молоко за 50 ₽ дают 280 ₽. Добавьте эспрессо — «Мой выбор» покажет 400 ₽. На второй точке круассан недоступен, хотя в первом меню он есть. Подробный [сценарий показа](docs/DEMO.md) занимает около трёх минут.

## Локальный запуск

Нужны Docker Engine и Docker Compose. Из корня репозитория:

```bash
cp .env.example .env
docker compose up -d --build
docker compose exec backend python -m app.demo_seed
```

В PowerShell первая команда — `Copy-Item .env.example .env`. `docker compose up -d --build` поднимает локальные компоненты одной командой; последний шаг добавляет тестовую «Кофейню Север». Повторный запуск сида не создаёт копии данных. Используйте чистую тестовую базу, если в локальной базе уже есть свои заведения.

| Адрес | Что открывается |
| --- | --- |
| `http://localhost:8080` | Приложение и гостевое меню |
| `http://localhost:8080/r/demo-sever` | Меню первой тестовой точки |
| `http://localhost:8080/r/demo-sever-park` | Меню второй точки со своим стоп-листом |
| `http://localhost:8080/manage` | Кабинет в локальном режиме разработки |
| `http://localhost:8000/docs` | Документация API |
| `http://localhost:8000/api/v1/health/ready` | Проверка готовности API |

Локальный вход включён только при `APP_ENV=development` и `DEV_AUTH_ENABLED=true`. Тестовый MAX ID указан в [.env.example](.env.example). На сервере с рабочим ботом нужен настоящий вход из MAX и отдельная роль администратора для тестового аккаунта. Секреты задаются в серверном `.env`; пример из репозитория для рабочего сервера не подходит.

Остановить контейнеры: `docker compose down`. Эта команда сохраняет том PostgreSQL. Посмотреть состояние и логи: `docker compose ps` и `docker compose logs --tail=100 backend frontend worker`.

## Устройство проекта

| Компонент | Роль | Где смотреть зависимости |
| --- | --- | --- |
| `frontend/` | React, TypeScript, Vite; гостевое меню и кабинет | `frontend/package-lock.json` |
| `backend/` | FastAPI, авторизация MAX, меню, цены и API | `backend/requirements.txt` |
| `postgres` | Хранение заведений, меню, доступов и событий | `compose.yaml` |
| `worker` | OCR и фоновые задачи | `backend/Dockerfile` |
| `mcp` | Необязательный доступ к черновику меню для внешнего помощника | [Инструкция MCP](docs/ai-and-mcp.md) |

`compose.yaml` запускает необходимые сервисы, а `backend/Dockerfile` и `frontend/Dockerfile` собирают образы. Для импорта сканов в образ backend включён Tesseract. ИИ-функциям нужен внешний OpenAI-совместимый шлюз и ключ `AI_API_KEY`; ручное редактирование от него не зависит. Настройка бота использует `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `PUBLIC_APP_URL` и параметры webhook. Полный список переменных и примеры значений находятся в [.env.example](.env.example).

Не добавляйте рабочие токены, пароли, персональные данные и `initData` в Git или логи. Доступ к меню другого заведения проверяется сервером; сама ссылка на кабинет прав не выдаёт.

## Проверка и API

```bash
docker compose config --quiet
docker compose --profile test run --rm tests
cd frontend && npm ci && npm run build && npm run test:unit && npm run test:browser
```

Интеграционные проверки запускайте на отдельной тестовой базе. `npm run test:live` пересоздаёт базу из `E2E_DATABASE_URL`, поэтому рабочую базу для него указывать нельзя. Браузерные тесты используют тестовый API; вход, кнопки и навигацию внутри MAX проверяйте по [чек-листу после развёртывания](docs/max-production-check.md).

В репозитории есть [OpenAPI 3.1](openapi.json), [DATA-API.yaml](DATA-API.yaml) с ролями и обязательными проверками, а также [тестовые данные](test-data/api-demo.json). OpenAPI можно обновить командой `python scripts/export_openapi.py` из каталога `backend/`. Для проверки живой версии нужны публичный HTTPS-адрес API и тестовый аккаунт с нужной ролью; адрес проекта указан в начале README. Версию запущенного кода удобно сверить с `git rev-parse HEAD` на сервере.
