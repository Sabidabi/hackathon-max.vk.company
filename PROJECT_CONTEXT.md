# Контекст проекта для команды и ИИ

Последнее обновление: 26.09.2026. Этот файл — точка входа, не рекламное описание готового продукта.

## Что строим

B2B SaaS для небольших кофеен, пекарен и кафе: владелец создаёт точку и меню, гость открывает его по ссылке или QR в доступном браузере/MAX. Дальнейшая цель — предзаказ на самовывоз с ЮKassa, экраном сотрудника, статусами, повтором заказа, приватным отзывом и отчётом.

Главная ценность: быстро запустить своё понятное цифровое меню без большой кассовой системы и без разработки отдельного приложения для каждого бизнеса. Гипотеза подписки обсуждалась около 2500 ₽/месяц; это не подтверждённый тариф и не доказанная экономика.

## Что делаем прямо сейчас

1. Анализируем и дорабатываем существующую заготовку, не переписываем её заново.
2. Цепочка «создать точку → категории/позиции → варианты и добавки → предпросмотр → публикация → QR» реализована локально. Она проверяется браузерной фикстурой, а миграции и серверные сценарии — локальной PostgreSQL.
3. Переделываем кабинет по запросу владельца: меньше текста, подсказки через Info, компактный список и отдельная карточка позиции.
4. Первый слой гибкости по образцу iiko реализован: **размеры, добавки, обязательные группы выбора**, включая доплаты по размеру и серверный расчёт. Полный паритет с iiko не обещан.
5. Автоматический вход из MAX, AI-композер карточек, draft-only MCP, расширенное оформление и антиспам-рассылки реализованы локально. Миграции проверены на локальной PostgreSQL; реальные провайдеры требуют отдельных тестовых credentials.
6. Готовим инструкции для команды и будущих ИИ-разработчиков.
7. Гостевое меню строим как каталог мобильного приложения ресторана: современная обложка, плавающий поиск, меню первым блоком, горизонтальные категории и карточки блюд в сетке. Базовые направления оформления — «Минимал», «Бистро», «Поп» и «Ночь».

Актуальные файлы: `docs/menu-editor-stage.md`, `docs/04-execution-backlog.md`, `MCP_README.md`, `docs/product-design-guide.md`, `docs/project-audit.md`, `docs/implementation-status.md`.

## Принятые решения

- Сохраняем React/TypeScript/Vite/MAX UI и FastAPI/SQLAlchemy/PostgreSQL/Alembic. Ранее предложенный TypeScript backend не повод переписывать работающий Python-код.
- Авторизованный владелец создаёт несколько точек. Создание профиля, роли владельца, меню и первого черновика происходит транзакционно. Опубликованные версии доступны в библиотеке для независимого копирования или восстановления в черновик другой своей точки.
- Наличие позиции можно менять в черновиках нескольких точек. Владелец приглашает сотрудников по MAX ID на роль точки; приглашение одноразовое, отзыв и смена роли доступны в кабинете. Коммерческий онбординг ещё нужен.
- Есть отдельные черновик и опубликованные снимки меню/оформления. Импорт не публикует результат автоматически.
- QR содержит постоянный гостевой URL, не сессию и не ссылку с правами администратора.
- Размер задаёт абсолютную цену позиции. Добавка прибавляет стоимость; для размера возможна отдельная доплата.
- Группы и отдельные добавки имеют лимиты. Обязательность группы задаётся минимальным количеством > 0. Расчёт опубликованной конфигурации выполняет сервер.
- Суммы — целые копейки, валюта текущего этапа RUB. Отсутствующая цена не должна тихо становиться нулём.
- Сложные возможности прячем в карточку позиции, а не усложняем основной экран.
- Публичное меню по умолчанию идёт перед «О нас» и другими редакционными блоками; на телефоне карточки располагаются по две в ряд.
- ИИ и MCP формируют проверяемое предложение с ревизией и не публикуют меню.
- Новостная рассылка доступна только подписавшимся пользователям из избранного; черновые изменения сообщений не создают.

## Что было в заготовке

Авторизация MAX с серверной проверкой и сессией, модели ресторанов/участников/меню/версий, ручной редактор, импорт файлов, локальный OCR и парсер, просмотр гостевого меню, конструктор оформления, Docker Compose и тесты. Импорт использует Tesseract/парсинг; отдельный GigaChat-композер теперь добавляет карточки по структурированному плану, но реальный credential не проверялся. Отметки в старом `docs/PLAN.md` не заменяют проверки.

## Что нельзя считать готовым

Платежи и возвраты, полноценные заказы/корзина/экран сотрудника, лимиты выдачи, расписание по дням и исключениям, полноценный учёт, производственные интеграции и аналитика. Приглашения сотрудников реализованы локально, но не проверены в настоящем MAX. Карта, бронирование столов, реклама и другие мессенджеры отложены. Генерация фоновых изображений и премиальные анимации запланированы после пилота. Конструктор конфигурации не равен интеграции с iiko или складской системе.

Точный список реализованного, незавершённого и результаты тестов — только в `docs/implementation-status.md`. Файлы с демо-фикстурами не являются производственной базой.

## Следующие этапы

1. Поднять отдельного тестового MAX-бота, HTTPS mini app и webhook; пройти вход, создание точки, публикацию, QR, AI-план и уведомление непосредственно внутри MAX. Параллельно закрыть проверки миграций на тестовой PostgreSQL.
2. Провести пилот с несколькими реальными кофейнями: время до публикации, число ручных исправлений импорта, ошибки редактора, читаемость QR. Не придумывать результаты пилота.
3. Перед продажами — структурированное расписание/часовой пояс, продавец и условия, защищённый онбординг, каталог со стабильными идентификаторами, серверная корзина и повторная проверка цены/доступности.
4. ЮKassa: тестовый режим, идемпотентность, проверка webhook, статусы и возвраты. Реальные операции только после соответствующей авторизации и приёмки.
5. Экран сотрудника, уведомления с повторными попытками, отчёт дня и повтор заказа. Только затем расширять продукт по результатам пилота.

## Где работать

Основной проект пользователя: `D:/hackathon-max.vk.company`. Документы бизнес-планирования первоначально находились в рабочем пространстве «Онлайн меню в мессенджере MAX»; их базовые версии перенесены в `docs/01-product-brief.md`, `02-mvp-specification.md`, `03-ai-constitution.md` для передачи команды.

Не читать и не печатать `.env` без конкретной необходимости. Не переносить его в демо, отчёты и фикстуры. Сохранять чужие незакоммиченные изменения. Не запускать интеграционные тесты против рабочей БД.

## Как продолжать с ИИ

Сначала прочитать `AGENTS.md`, этот контекст и статус реализации. Проверить `git status` и фактический код. Выбрать ближайшую незакрытую задачу в согласованном этапе. Если код расходится с документами — исследовать, зафиксировать разницу, не доверять формулировке «готово» без проверки. После работы обновить статус с командами, результатами и ограничениями. Дизайн менять по `docs/product-design-guide.md`. Каждый push выполнять только после сборки, тестов и проверки запуска; коммит обязан описывать сделанный результат.
